# Quick Start Guide

После установки и запуска XAgent настройте его по шагам ниже.

## 1. Создание проекта

1. Откройте веб-интерфейс: `http://<host>:<port>` (по умолчанию порт `8080`)
2. Нажмите **Create Project**
3. Заполните:
   - **Project Name** - произвольное имя (например, `production`)
   - **Resource Provider** - `Other`
4. Нажмите **Create**

## 2. Настройка моделей

Перейдите в **Models** (боковое меню проекта).

1. Нажмите **Probe** напротив доступных моделей - XAgent проверит подключение и поддерживаемые возможности (Tool Calling, Structured Output, Reasoning)
2. Включите нужные модели переключателем в колонке **Enabled**
3. Установите одну модель как **Default** - она будет использоваться для новых чатов и задач мониторинга

> **Совет**: задайте размер контекстного окна модели в поле **Context Window**: `120k`.

## 3. Подключение к базе данных

### Подготовка на стороне PostgreSQL

Перед добавлением сервера подготовьте целевой PostgreSQL.

#### 1. Создание пользователя и назначение прав

```sql
-- Создание выделенного пользователя
CREATE USER xagent WITH PASSWORD '<надёжный_пароль>';

-- Чтение системной статистики (pg_stat_activity, pg_locks, pg_settings,
-- pg_stat_replication, pg_stat_wal и др.)
GRANT pg_monitor TO xagent;

-- Чтение данных из пользовательских таблиц (PostgreSQL 14+)
-- Необходимо для: просмотра pg_stats (статистика колонок), EXPLAIN запросов,
-- анализа структуры таблиц, сэмплирования данных, SQL Query SubAgent
GRANT pg_read_all_data TO xagent;
```

> **Ограниченный доступ**: вместо `pg_read_all_data` можно дать доступ к конкретным схемам, но это ограничит функциональность агента:
>
> ```sql
> GRANT USAGE ON SCHEMA public TO xagent;
> GRANT SELECT ON ALL TABLES IN SCHEMA public TO xagent;
> ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO xagent;
> ```
>
> При таком варианте не будут работать: EXPLAIN для запросов к другим схемам, статистика колонок (`pg_stats`) вне разрешённых схем, SQL Query SubAgent для таблиц вне разрешённых схем.

#### 2. Настройка расширения pg_stat_statements

Расширение `pg_stat_statements` **обязательно** - без него агент не сможет анализировать медленные запросы и строить планы выполнения по queryId.

Добавьте в `postgresql.conf`:

```ini
shared_preload_libraries = 'pg_stat_statements'
```

> После правки `shared_preload_libraries` PostgreSQL нужно **перезапустить**.

Затем создайте расширение в целевой базе данных:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```

Опционально, для более точного анализа bloat индексов:

```sql
CREATE EXTENSION IF NOT EXISTS pgstattuple;
```

#### 3. Имя машины (Machine Name)

Чтобы сопоставлять сервер с его логами (VictoriaLogs), метриками (VictoriaMetrics) и алертами (Webhooks), XAgent использует **имя машины** - поле **Machine Name** у сервера. Укажите его вручную при добавлении или редактировании сервера: это то имя, под которым сервер публикует свои логи и метрики (как правило, FQDN хоста - например, вывод команды `hostname -f`). Поле необязательное - его можно оставить пустым и заполнить позже; пока оно не задано, сопоставление логов и метрик для этого сервера не выполняется.

> **Кластер PostgreSQL**: если вы работаете с кластером (Patroni, Pacemaker/Corosync, repmgr и т.д.), есть два варианта. Для полноценного мониторинга всех узлов добавьте сервер типа **Patroni** (узлы и роли обнаруживаются автоматически) или **Generic Cluster** (узлы задаёте сами) - см. [targets.md](targets.md). Если же нужен только текущий мастер, проще создать **standalone-сервер на VIP-адрес**, привязанный к роли primary: агент всегда будет работать с текущим мастером, даже после переключения (failover/switchover). Для каждого узла кластера имя машины также задаётся вручную.

> **PostgreSQL 15**: опция `EXPLAIN (GENERIC_PLAN)` доступна начиная с PostgreSQL 16. На PostgreSQL 15 агент не сможет строить планы для параметризованных запросов из `pg_stat_statements` (запросы с `$1`, `$2`, ...), но скажет об этом, а не сломается.

### Добавление сервера в XAgent

1. Перейдите в **Targets** → **Add New Target**
2. Тип оставьте **Standalone** (одна база) и заполните:
   - **Target Name** - имя сервера (например, `prod-primary`)
   - **Connection String** - строка подключения: `postgres://xagent:<пароль>@<host>:5432/<database>`
3. XAgent автоматически:
   - Проверит соединение
   - Соберёт информацию о базе (таблицы, расширения, настройки)

> Кроме одиночной базы можно добавить **кластер** (Generic или Patroni). Подробнее о модели серверов - в [targets.md](targets.md).

## 4. Настройка мониторинга (опционально)

Перейдите в **Monitoring** → **Add Schedule**.

Параметры расписания:

| Параметр               | Описание                                                                                                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Database**           | Выберите сервер из списка                                                                                                                                                              |
| **Playbook**           | Сценарий анализа (например, `generalTroubleshooting`)                                                                                                                                  |
| **Model**              | LLM-модель для выполнения                                                                                                                                                              |
| **Schedule Type**      | `cron` (фиксированное расписание - графический конструктор или ручной ввод cron-выражения) или `automatic` (агент сам выбирает время следующего запуска в пределах мин/макс интервала) |
| **Time Range**         | Глубина анализа логов и метрик (`15m`, `1h`, `6h`, `24h`, `7d`, `30d`)                                                                                                                                     |
| **Notification Level** | Уровень уведомлений: `info`, `warning`, `alert`                                                                                                                                        |

Найденные проблемы агент заводит как **записи об инцидентах** в разделе **Alerts**. Запись открывается один раз и закрывается один раз - повторный прогон, нашедший ту же проблему, дописывает подтверждение в существующую запись, а не заводит новую. Закрывается запись всегда с названной причиной: проблема ушла, уровень опустился ниже порога уведомления, запись закрыл человек, удалён источник (расписание, сервер или вебхук), расследование не дошло до вывода. Если для проекта настроен Slack (раздел **Notifications**), открытие и закрытие записи уходят в канал.

### Запуск плейбука вручную

Плейбук можно запустить двумя способами:

1. **Через UI**: в разделе **Playbooks** нажмите кнопку запуска напротив нужного плейбука, выберите сервер и модель
2. **Через чат**: откройте чат, выберите сервер и модель, затем напишите `Run playbook generalTroubleshooting`

Агент выполнит все шаги плейбука и покажет результат.

### Создание собственного плейбука

1. Перейдите в **Playbooks** → **Create Playbook**
2. Заполните:
   - **Name** - имя плейбука (латиницей, без пробелов, например `proactiveHealthCheck`)
   - **Description** - описание назначения
   - **Content** - пошаговая инструкция для агента (на английском языке)
   - **Allow Non-Interactive** - включите, если плейбук будет использоваться в расписаниях и вебхуках
3. Нажмите **Save**

Пример плейбука: [example-playbook-proactive-health-check.md](example-playbook-proactive-health-check.md)

## 5. Уведомления в Slack (опционально)

Перейдите в **Notifications** (боковое меню проекта).

1. Создайте в Slack входящий вебхук (Incoming Webhook) для нужного канала
2. Вставьте его URL в поле на странице и сохраните

После этого агент сам пишет в канал, когда заводит и когда закрывает запись об инциденте. Ссылка в сообщении ведёт на карточку записи в разделе **Alerts**.

## 6. Настройка вебхуков (опционально)

По алерту от AlertManager вебхук сам запускает плейбук расследования.

Подробная инструкция: [webhooks.md](webhooks.md)

## 7. Команды на сервере (опционально)

По умолчанию агент только читает базу. Если нужно, чтобы он мог **предложить** команду, меняющую данные или конфигурацию, включите это явно:

1. **Targets** → сервер → **Settings** → переключатель **Allow changes**
2. У участника, который будет одобрять команды, должна быть роль **operator** или **owner** (роли настраиваются в **Settings** → вкладка **Members**)

Как это выглядит в работе:

1. Агент показывает в чате карточку с текстом команды, оценкой риска (`none` / `reversible` / `irreversible`) и пояснением, что стоит на кону
2. Человек нажимает **Run** или **Decline**; для необратимой команды подтверждение запрашивается дважды
3. Выполнение идёт на сервере и переживает закрытие вкладки; выполняющуюся команду можно остановить кнопкой **Cancel**
4. Все команды сервера с их выводом и результатом видны на вкладке **Commands** этого сервера

Одновременно на одном сервере выполняется одна изменяющая команда.

**Длинные чтения.** Тяжёлый запрос, которому не хватает обычного лимита времени (подсчёт по большой таблице, отчёт по всей истории), агент предлагает той же карточкой с одобрением. Такой запрос держит открытым снимок данных, поэтому база не может убирать старые версии изменившихся строк - на активной таблице это заметный рост таблицы и индексов, и карточка об этом предупреждает. Длинные чтения доступны, когда у сервера включён **Enable SQL Mode** и у участника есть право выполнять запросы (роль **operator** или **owner**). Сам переключатель **Enable SQL Mode** остаётся серым, пока в `.env` не задано `SQL_MODE=true`. Количество одновременных длинных чтений на сервер и предельное время задаются переменными окружения `LONG_READ_MAX_PER_TARGET` (по умолчанию 3) и `LONG_READ_TIME_LIMIT_SECS` (по умолчанию 4 часа), а `LONG_READ_DISABLED=true` убирает эту возможность целиком.

## Проверка работоспособности

После настройки убедитесь, что всё работает:

1. **Чат**: откройте чат с агентом и задайте вопрос о состоянии базы, например: _«Покажи текущую нагрузку на базу»_
2. **Мониторинг**: если настроено расписание, дождитесь первого запуска и проверьте результат в разделе **Monitoring**
3. **Сервер**: в разделе **Targets** убедитесь, что статус сервера - **Healthy**

## Что агент умеет помимо анализа

- **Справочник PostgreSQL внутри установки** - в образ встроена официальная документация PostgreSQL 14-18. Агент ищет по ней и цитирует страницы, отвечая по той версии, которая стоит на вашем сервере. Если версия сервера ещё не определена, агент спросит её, а не ответит по чужой.
- **Кластеры** - Patroni и кластеры на другом ПО репликации: роли узлов, отставание реплик, расхождение настроек между узлами. См. [targets.md](targets.md).
- **Память по серверу** - агент ведёт заметки о проекте и его базах и ищет по прошлым чатам и прогонам мониторинга этого сервера, поэтому новая сессия начинается не с чистого листа.
- **Записи об инцидентах и уведомления в Slack** - раздел **Alerts** и сообщения в канал при открытии и закрытии записи.
- **Команды с одобрением человека** - при явно включённом переключателе (см. раздел 7 выше).
- **Совместная работа в чате** - в одном чате может участвовать несколько человек проекта; сообщения выполняются по очереди, видно, кто сейчас в чате.
- **Ответ считается на сервере** - генерация не привязана к вкладке: страницу можно закрыть или перезагрузить, а вернувшись, увидеть ответ целиком. Ответ, который пишется прямо сейчас, показывается при каждом открытии переписки - и с другого устройства тоже. Потерянное соединение восстанавливается, и пропущенное догоняется из истории.

## Ограничения

- **Изменения - только по одобрению человека** - сам по себе агент базу не меняет: он анализирует и предлагает. Изменяющую команду он может предложить, только если у сервера включён переключатель **Allow changes**, и она выполняется после явного нажатия человеком. Всё остальное (перезапуск сервисов, правка `postgresql.conf`, действия на уровне ОС) выполняется вручную.
- **Только vanilla PostgreSQL** - агент не знает про форки (Postgres Pro, Tantor и др.). Все рекомендации и анализ основаны на возможностях стандартного PostgreSQL.
- **Нет анализа стратегий бэкапа** - агент видит состояние архивации WAL, но не разбирает схемы резервного копирования (pg_basebackup, pgBackRest, WAL-G) и не оценивает их пригодность.
- **Нет интеграции с провайдерами уведомлений, кроме Slack** - отсутствует встроенная отправка в Telegram, email, Mattermost.
- **Нет интеграции с тикет-системами** - агент не умеет создавать задачи в Jira или других ticketing-системах. Найденные проблемы нужно оформлять вручную.
- **Только страницы документации, поставляемые в образе** - версии PostgreSQL за пределами 14-18 и внешние источники (статьи, документация расширений, форки) агенту недоступны.

Это свойства продукта, задуманные такими. Отдельно ведётся список ошибок текущей версии и обходных путей к ним: [known-issues.md](known-issues.md). Что появилось в этой версии - в [changelog.md](changelog.md).
