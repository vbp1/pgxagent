# Серверы (Targets): архитектура и справочник

Это справочное руководство по модели **Targets** («Серверы») — что это, из чего состоит и как настраивается.

---

## Что такое сервер

**Сервер (target)** — это объект мониторинга: одна база PostgreSQL или целый кластер. Один сервер описывает один наблюдаемый объект целиком, включая доступ к базе, права (приватность/владелец), ярлыки для метрик и логов и настройки безопасности соединения.

### Типы серверов

| Тип               | Что это                                                                 | Откуда берутся узлы и роли                                                                 |
| ----------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Standalone**    | Одна база PostgreSQL                                                     | Один узел; роли не нужны                                                                    |
| **Generic Cluster** | Кластер на любом ПО репликации/переключения (repmgr, pg_auto_failover, Stolon, Pacemaker/PAF, ручное переключение) | Список узлов задаёте вы; роль каждого узла читается **прямо у PostgreSQL** (`pg_is_in_recovery()`) |
| **Patroni Cluster** | Кластер под управлением Patroni                                        | Узлы и роли **обнаруживаются автоматически** через Patroni REST API (`/cluster`)            |

Тип задаётся при создании и **не меняется** потом — чтобы сменить тип, пересоздайте сервер. Типы `rds`/`gcp` зарезервированы на будущее.

## Модель узла: три независимые «плоскости» адреса

У узла кластера есть три адресоподобных свойства, которые **нельзя смешивать** — они нужны для разных целей и могут отличаться друг от друга:

| Плоскость              | Поля                       | Назначение                                                                                 |
| ---------------------- | -------------------------- | ------------------------------------------------------------------------------------------ |
| **Идентичность**       | `nodeName`                 | Стабильный ключ узла (имя Patroni-участника или ваша метка). По нему всё «сшивается» между обновлениями топологии; переживает смену адреса и роли |
| **Адрес для агента**   | `connectHost` / `connectPort` | Куда агент **реально дозванивается** до базы. Может отличаться от того, что сообщает Patroni (кластер часто в отдельной сети) |
| **Имя хоста для меток**| `hostname` / `port`        | Метка `{{hostname}}` в селекторах метрик/логов и идентичность для сопоставления вебхуков. Может отличаться и от `nodeName`, и от `connectHost` |

Почему один общий хост не может описать кластер: агент должен достучаться до **каждого** узла отдельно (роль каждого, настройки каждого, метрики каждого), поэтому адрес — всегда **по узлу**. У кластера общий вход (логин/пароль/база) **не содержит хоста**.

**Переопределение адреса узла.** Адрес для агента (`connectHost`/`connectPort`) предзаполняется при обнаружении, но его можно отредактировать. Правка сохраняется в постоянное переопределение (привязано к `nodeName`) и **переживает пере-обнаружение и даже удаление-и-возврат узла** — полезно, когда агент и кластер в разных сетях.

## Ярлыки мониторинга (селекторы)

Чтобы агент знал, какие графики и журналы относятся к серверу, у сервера задаются **селекторы** — шаблоны запросов к вашей системе мониторинга. Настраиваются прямо в форме сервера (блок **Monitoring Labels**), с живым предпросмотром.

### Плейсхолдер

В шаблонах поддерживается **один** плейсхолдер — `{{hostname}}`, он подставляет имя хоста узла. Это единственный раскрываемый токен; если в шаблоне опечатка или незнакомый плейсхолдер (`{{port}}`, `{{cluster}}` и т.п.), система предупредит об этом при сохранении.

> Одиночные фигурные скобки (например, в LogsQL) не трогаются — реагирует только парный `{{…}}`.

### Поля селекторов

| Поле                             | Что задаёт                                                          | Пример                                            |
| -------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------- |
| `metricsNodeSelectorTemplate`    | Базовый ярлык узла для метрик (PromQL)                              | `node_name="{{hostname}}"`                        |
| `metricsNodeSelectorRules`       | Уточнения по префиксу имени метрики (массив `{prefix, template}`)   | `[{ prefix: "node_", template: "_node_id=\"{{hostname}}\"" }]` |
| `logsStreamSelectorTemplate`     | Поток логов (LogsQL)                                                | `hostname:{{hostname}} AND app_name:postgresql`   |
| `metricsClusterSelectorTemplate` | Ярлык уровня кластера для метрик (только у кластеров)               | `cluster_name="{{hostname}}"`                     |

Правила по префиксу позволяют разным семействам метрик использовать разные ярлыки. При запросе выбирается правило с **самым длинным совпадающим префиксом**; если ни одно не подошло — базовый шаблон узла.

### Наборы правил (Selector Presets)

Чтобы не вводить шаблоны вручную для каждого сервера, есть **наборы** — на странице **Selector Presets** (группа настроек в боковом меню).

- **Встроенные** наборы доступны только для чтения. Поставляются три:

  | Набор            | Ярлык узла (метрики)        | Поток логов                                      |
  | ---------------- | --------------------------- | ------------------------------------------------- |
  | **Spectrum**     | `node_name="{{hostname}}"`  | `hostname:{{hostname}} AND app_name:postgresql`   |
  | **Node Exporter**| `instance="{{hostname}}"`   | `hostname:{{hostname}}`                            |
  | **pgwatch**      | `host="{{hostname}}"`       | `host:{{hostname}}`                                |

- **Свои** наборы можно создавать, редактировать и удалять; они появятся в выпадающем списке формы сервера.

**Важно — снимок, а не ссылка.** Когда вы применяете набор, его значения **копируются** в поля сервера. Изменив набор позже, вы **не** меняете уже настроенные серверы. Привязка к набору хранится только как пометка о происхождении.

### Живая проверка

В блоке **Monitoring Labels** есть две возможности увидеть результат:

- **Предпросмотр** — статично показывает, во что развернётся шаблон для примера имени хоста.
- **Кнопка проверки** — отправляет реальный запрос в VictoriaMetrics/VictoriaLogs с развёрнутым селектором и сообщает, нашлись ли по нему данные. Это помогает сразу поймать опечатку в ярлыке.

## Безопасность подключения (TLS)

У базы и у Patroni REST API — **независимые** наборы настроек TLS (можно проверять сертификат базы, но не Patroni, и наоборот).

### База (`Database Security (TLS)`)

| Настройка                | Значение                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------- |
| **SSL Mode**             | `disable` (без шифрования) · `require` (шифровать, не проверять) · `verify-ca` (проверять цепочку) · `verify-full` (проверять цепочку и имя хоста) |
| **CA-сертификат**        | PEM корневого/корпоративного CA для проверки сертификата сервера; пусто ⇒ системные CA   |
| **Клиентский сертификат**| PEM для взаимной аутентификации (mutual-TLS)                                             |
| **Клиентский ключ**      | PEM-ключ — **секрет** (маскируется, доступ по правам)                                    |
| **Verify Server Certificate** | Переключатель: явно отключить проверку сертификата сервера (шифрование без проверки) |

Эти настройки применяются и к standalone, и к кластерам (у кластеров нет строки подключения, поэтому режим хранится отдельным полем).

### Patroni REST API

Тот же набор для REST-клиента: `http://` vs `https://` (по схеме URL), системный/свой CA/без проверки, аутентификация none/basic/клиентский сертификат (mTLS). У Patroni в режиме `verify_client: required` без клиентского сертификата отвергается даже чтение `/cluster` — поэтому mTLS обязателен для подключения к таким кластерам.

## Кластеры: обнаружение, роли, топология

### Обнаружение узлов

- **Patroni** — система вызывает `GET {patroniApiUrl}/cluster`, извлекает участников, их адреса и роли, и создаёт узлы автоматически. Адрес для агента предзаполняется из ответа и остаётся редактируемым.
- **Generic Cluster** — список узлов задаёте вы (адрес + порт каждого). Опционально можно попросить агента **подсказать** стендбаи: он подключится к указанному праймери, прочитает `pg_stat_replication` и предложит подключённые реплики. Это подсказка best-effort (видит только текущие подключённые реплики, отдаёт IP `client_addr`, не видит каскадные/отключённые узлы) — членство всё равно остаётся за вами.

### Роли по двум осям

Узел несёт **две независимые роли**, которые обычно совпадают, но расходятся ровно тогда, когда это важнее всего:

- **`pgRole`** — что PostgreSQL **на самом деле** сейчас: `primary` (`pg_is_in_recovery() = false`, принимает запись) или `standby` (в восстановлении). Читается прямо у живого узла, помечается `roleConfirmed`.
- **`clusterRole`** — что говорит оркестратор: `leader` (держит блокировку лидера в DCS), `replica`, `sync_standby`, `standby_leader`, `quorum_standby`. Источник — Patroni `/cluster`. У generic-кластера отсутствует (нет блокировки).

`pgRole` подтверждается у PostgreSQL **даже когда API доступен** (перекрёстная проверка) и остаётся **единственным** источником роли, когда API недоступен — а это частый случай ровно во время инцидента.

### Особые состояния

- **Split-brain (расщепление).** Опасный случай — **два** PostgreSQL-праймери при одном `leader`. Легитимный праймери — тот, у кого `clusterRole = leader`; любой другой узел с `pgRole = primary` — застрявший/огороженный праймери, не успевший понизиться. У generic-кластера лидера нет, поэтому расщепление видно лишь как «≥ 2 достижимых праймери» без указания легитимного.
- **Standby-кластер.** Кластер, реплицирующийся от внешнего апстрима, **законно** не имеет ни одного `primary` (его лидер — `standby_leader`, сам в восстановлении). Это валидная топология, а не ошибка.

### Обновление топологии

Карта кластера обновляется по нескольким триггерам: на плановых прогонах мониторинга, в фоне при старте чата (чат открывается сразу на сохранённой карте), и **лениво** — когда инструмент кластера запускается, а данные устарели. Порог устаревания не короче TTL кластера (Patroni и так отдаёт `/cluster` из кэша DCS, обычно ~30 c). Для Patroni обновление добавляет новые узлы и **удаляет** узлы, пропавшие из `/cluster` на несколько проверок подряд (с задержкой против мерцания); для generic-кластера членство **не** трогается автоматически — узлы остаются, пока вы их не уберёте.

### Бережные таймауты

Каждое соединение с узлом и каждый запрос к Patroni API ограничены по времени, а узлы опрашиваются независимо: один недоступный узел портит только свой собственный статус и **никогда не подвешивает** обновление всей топологии.

## Сбор сведений о схеме

Кэш сведений о базе (таблицы, расширения, настройки) хранится по узлам:

- «Реплицируемые» категории (таблицы, расширения) собираются **один раз с праймери**.
- «Поузловые» категории (настройки производительности, vacuum) собираются **с каждого узла** — так видно расхождение конфигурации между узлами.

Кэш одноразовый: он удаляется вместе с узлом.

## Сопоставление вебхуков

Алерт сопоставляется с сервером по **сохранённому** имени хоста узла (`target_nodes.hostname`) — быстрым поиском по индексу в пределах проекта, без обращения к базам. В обычном случае «одна база на хост» имя хоста уникально и совпадение однозначно; при нескольких базах на одном хосте идентичность — пара `(hostname, port)`, и алерт уточняется его лейблами. Если узел так и не сузился до одного — фиксируется контролируемое состояние «неоднозначное совпадение», а не догадка. Для кластера расследование привязывается к узлу, на котором сработал алерт, с доступом к контексту всего кластера. Подробнее — в [webhooks.md](webhooks.md).

## Права и секреты

Серверы наследуют ту же модель прав, что и прежние подключения: приватность (`public`/`private`) + владелец, тонкие права участников проекта, аудит. Сервером по умолчанию может быть **только публичный** сервер — чтобы у каждого участника значение по умолчанию было рабочим.

Пять полей хранятся как **секреты** (маскируются на проводе, раскрываются по правам, аудируются при break-glass): строка подключения standalone, пароль БД кластера, пароль Patroni API и два клиентских TLS-ключа (базы и Patroni).

Удаление сервера **заблокировано**, пока на него есть расписания мониторинга — чтобы не стереть наблюдение случайным кликом.
