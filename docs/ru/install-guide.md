# Руководство по установке XAgent

## Системные требования

| Компонент      | Минимум                               | Рекомендуется                                   |
| -------------- | ------------------------------------- | ----------------------------------------------- |
| ОС             | Linux                                 | Ubuntu 22.04 LTS                                |
| Docker Engine  | 20.10+                                | 24.0+                                           |
| Docker Compose | v2.0+                                 | v2.20+                                          |
| RAM            | 4 ГБ                                  | 8-16 ГБ                                         |
| Диск           | 15 ГБ                                 | 30+ ГБ                                          |
| Сеть           | Сеть для доступа к целевым PostgreSQL | Сеть для доступа к целевым PostgreSQL           |
| Часовой пояс   | Любой                                 | Часы хоста ни на что не влияют: контейнер работает по UTC. Cron-выражения расписаний читаются в поясе контейнера; чтобы читать их в другом поясе, задайте `TZ` в `.env` |
| **LLM**        | Один из вариантов ниже                | Облачный API (DeepSeek)                         |

**Варианты подключения LLM**:

- **Облачный API** - требуется доступ в интернет к API-провайдеру (DeepSeek, BotHub, VseLLM и др.). Подробнее в разделе [Подготовка LLM-провайдера](#подготовка-llm-провайдера).
- **Локальный LLM** - доступ в интернет не требуется. Используйте Ollama, vLLM или любой OpenAI-совместимый сервер в локальной сети.

> XAgent не устанавливает Docker. Если Docker не установлен, поставьте его по инструкции вашего дистрибутива Linux.

## Подготовка LLM-провайдера

До установки выберите модель и площадку, получите адрес API и ключ доступа.

### Рекомендованный вариант: DeepSeek V4.1 Flash

- API: `https://api.deepseek.com`
- Модель: `OPENAI_MODEL=deepseek-flash`
- Тип в установщике: **OpenAI-compatible** (`OPENAI_API_TYPE=compatible`)

На этом сочетании проверены запрос к базе и поиск документации в XAgent 0.7.0.
По [документации DeepSeek](https://api-docs.deepseek.com/en/), имя `deepseek-flash` сейчас соответствует DeepSeek-V4.1-Flash-1017.
Старое имя `deepseek-v4-flash` оставлено для совместимости; для новой установки используйте `deepseek-flash`.

### Выбор модели

| Модель | Когда выбирать | Имя у разработчика |
| --- | --- | --- |
| DeepSeek V4.1 Flash | Основной выбор для 0.7.0; проверен через API DeepSeek | `deepseek-flash` |
| GLM-5.3 | Альтернатива DeepSeek | `glm-5.3` |
| Qwen3.8 Max | Альтернатива DeepSeek | `qwen3.8-max` |
| gpt-oss-120b | Для локального запуска; требования зависят от формата весов и длины контекста | Имя, заданное локальным сервером |

Перед использованием другой модели откройте **Models**, выполните **Probe**, включите модель и выберите её по умолчанию.
Затем задайте в чате вопрос, который требует запроса к тестовой базе.
Успешная проверка доступности модели сама по себе не подтверждает качество её работы с инструментами XAgent.

### Площадки и имена моделей

Адреса и примеры имён сверены по документации площадок 12 ноября 2026 года.
Для одной модели площадки используют разные имена. Копируйте имя из каталога выбранной площадки.

| Площадка | Base URL | `OPENAI_API_TYPE` | Пример имени DeepSeek V4.1 Flash |
| --- | --- | --- | --- |
| [DeepSeek](https://api-docs.deepseek.com/en/) | `https://api.deepseek.com` | `compatible` | `deepseek-flash` |
| [BotHub](https://bothub.chat/deepseek-v4.1-flash-1017) | `https://bothub.chat/api/v2/openai/v1` | `openrouter` | `deepseek-v4.1-flash-1017` |
| [VseLLM](https://vsellm.ru/provider/VSELLM) | `https://api.vsellm.ru/v1` | `compatible` | `deepseek/deepseek-v4.1-flash` |

В каталоге VseLLM модель Qwen3.8 Max указана как `qwen/qwen3.8-2.4t-a95b`; не переносите имя `qwen/qwen3.8-max` с другой площадки.
Наличие модели в каталоге не заменяет проверку её работы через выбранную площадку в XAgent.

> **`OPENAI_API_TYPE`**: `compatible` — стандартный OpenAI-совместимый API. `openrouter` — OpenRouter и совместимые с ним прокси, включая BotHub. В этом режиме суффикс `:provider` в имени модели задаёт `provider.only` в запросе; например, `deepseek/deepseek-v4.1-flash:DeepSeek`. Используйте его, только если площадка поддерживает нужного поставщика. Если `OPENAI_BASE_URL` задан, а `OPENAI_API_TYPE` — нет, используется `compatible`.

### Другие провайдеры

| Тип в инсталляторе    | Что нужно                                                                         |
| --------------------- | --------------------------------------------------------------------------------- |
| OpenAI-compatible API | Base URL и API-ключ любого OpenAI-совместимого сервера (например, локальный vLLM) |
| OpenAI (native)       | API-ключ OpenAI                                                                   |

## Установка

### 1. Получение пакета

Выпускается два архива одной и той же версии - выберите по тому, есть ли на сервере интернет.

| Архив                                     | Размер   | Для чего                                                                       |
| ----------------------------------------- | -------- | ------------------------------------------------------------------------------ |
| `xagent-<version>-linux-amd64-online.zip`  | ~35 МБ   | Сервер с доступом в интернет: образы скачиваются при установке из Docker Hub    |
| `xagent-<version>-linux-amd64-offline.zip` | ~320 МБ  | Закрытый контур: все образы лежат внутри архива, сеть при установке не нужна    |

Внутри архивы одинаковы, кроме каталога образов.

Проще всего одной командой - она скачает свежий выпуск, сверит его с опубликованной контрольной суммой
и распакует:

```bash
curl -fsSL https://raw.githubusercontent.com/vbp1/pgxagent/main/install.sh | bash
```

Ключи: `--version <x.y.z>` - взять определённый выпуск, `--dir <путь>` - распаковать в другой каталог,
`--offline` - взять архив с образами внутри. Установщик команда не запускает: он задаёт вопросы,
а у скрипта, пущенного через трубу, нет терминала, чтобы их задать, поэтому в конце она печатает
команду для следующего шага.

Архивы можно скачать и вручную - со [страницы выпусков](https://github.com/vbp1/pgxagent/releases).

В образ приложения входит официальная документация PostgreSQL 14-18: агент ищет по ней и цитирует страницы, не обращаясь в интернет. После первого запуска она загружается в базу агента в фоне - сервис при этом работает, а поиск по документации становится доступен по мере загрузки.

Сетевой архив скачивает образы **без учётной записи**: ни логин, ни пароль Docker Hub не нужны и не
запрашиваются. Образ приложения скачивается по точному отпечатку, записанному в `manifest.json`, -
это подтверждает, что хранилище отдало ровно ту сборку, которая выпущена под этой версией.

### 2. Распаковка и проверка целостности

Если архив скачан вручную, сверьте его с контрольной суммой, опубликованной **рядом** с ним. В файле
сумм перечислены оба архива, поэтому берите строку того, который скачали:

```bash
grep xagent-<version>-linux-amd64-online.zip SHA256SUMS-<version>.txt | sha256sum -c
unzip xagent-<version>-linux-amd64-online.zip
cd xagent-<version>
./xagent-installer verify
```

Это две разные проверки. Первая отвечает на вопрос «дошёл ли архив целым»; список контрольных сумм
лежит рядом с архивом, а не внутри него, потому что список внутри архива за сам архив поручиться
не может. `verify` отвечает на другой вопрос: «совпадают ли файлы внутри с описью, которая с ними
приехала».

Команда `verify` проверяет SHA256-хеши всех файлов пакета по `manifest.json`. Для ручной проверки также доступен файл `SHA256SUMS` (`sha256sum -c SHA256SUMS`).

### 3. Запуск установки

```bash
sudo ./xagent-installer install --path /opt/xagent --up
```

Параметры:

- `--path <dir>` - директория установки (по умолчанию `/opt/xagent`)
- `--up` - автоматически запустить XAgent после установки
- `--offline` - брать образы только из архива, в сеть не обращаться
- `--online` - скачать образы, даже если они лежат в архиве

Без этих ключей источник выбирается сам: образы лежат рядом - грузим их, нет - скачиваем. Ключи
взаимоисключающие. Скачивание идёт через сам Docker, поэтому на машине с выходом в интернет через
посредника (прокси) настраивать нужно **Docker**, а не окружение установщика: посредник, заданный в
настройках демона, работает и здесь.

Инсталлятор запустит интерактивный визард:

1. **Общие настройки** - порт, URL (`https://`, см. [HTTPS и сертификат](#https-и-сертификат)), учётные данные PostgreSQL, `AUTH_TRUST_HOST`
   - **Сертификат** - пути к своему сертификату и его ключу (PEM); пустой ответ - установщик сделает самоподписанный
2. **Аутентификация** - опционально: OpenID SSO
3. **LLM-провайдер** - выбор и настройка (обязательно)
4. **Интеграции** - опционально: VictoriaLogs, VictoriaMetrics
5. **Язык агента** - English / Русский (записывается в `.env` как `AGENT_LANGUAGE`); проект может выбрать свой в настройках

`AUTH_SECRET` и `CORE_SECRET` визард генерирует сам, без запроса. Пароль PostgreSQL генерируется, если
оставить его запрос пустым.

Вход через внешнего поставщика включают три переменные `AUTH_OPENID_*`. У поставщика зарегистрируйте
адрес возврата `<URL установки>/api/auth/callback/default`. Вход по паролю остаётся на странице входа
всегда: суперадминистратор установки заходит паролем, кнопка входа через поставщика встаёт рядом с
формой.

Всё, что может отказать, проверяется **до** визарда и до создания каталога: доступность образов в
хранилище и свободное место. Отказ на этом этапе не оставляет следов на машине - можно исправить
причину и запустить установку заново.

После завершения визарда инсталлятор:

- Получит образы: скачает (с показом хода) или загрузит из архива
- Создаст директорию с конфигурацией
- Запишет `.env` (chmod 0600)
- Положит файлы HTTPS-входа в `proxy/`, а ваш сертификат, если он указан, - в `certs/`
- Запустит стек (если указан `--up`)

Уже полученные образы повторно не скачиваются: решение принимается по отпечатку, поэтому повторный
запуск после оборванного скачивания продолжает с того, чего не хватает.

### 4. Проверка работы

```bash
cd /opt/xagent

# Статус контейнеров
docker compose ps

# Логи ядра и веб-интерфейса
docker compose logs -f xagent-core xagent-web
```

Откройте в браузере: `https://<host>:<port>` (по умолчанию порт `8080`). Адрес `http://` на том же порту
сам переходит на `https://`. С самоподписанным сертификатом браузер один раз предупредит о нём; см.
[HTTPS и сертификат](#https-и-сертификат).

### 5. Первый вход

При первом открытии страница входа показывает форму **Create the superadmin**: имя пользователя,
необязательное отображаемое имя и пароль. Эта учётная запись администрирует установку и выдаёт доступ
всем остальным. Форма показывается, пока в установке нет суперадминистратора с паролем; после этого
страница показывает обычную форму **Sign in** (имя пользователя или email и пароль).

Если заданы переменные `AUTH_OPENID_*`, под любой из форм стоит кнопка
**Sign in with your identity provider**.

## Обновление

### 1. Распаковка нового пакета

```bash
unzip xagent-<new-version>-linux-amd64-online.zip
cd xagent-<new-version>
```

Обновление принимает те же ключи `--offline` и `--online`. Образы получаются **до** остановки стенда:
если сеть отказала, работающая установка остаётся нетронутой и продолжает работать.

### 2. Запуск обновления

```bash
sudo ./xagent-installer update --path /opt/xagent --backup full --up
```

Параметры:

- `--path <dir>` - директория существующей установки
- `--backup <mode>` - режим бэкапа перед обновлением:
  - `none` - без бэкапа
  - `files` - бэкап конфигурации (по умолчанию)
  - `full` - бэкап конфигурации + данных PostgreSQL
- `--up` - автоматически запустить после обновления

Обновление, по шагам:

- Получает образы - скачивает или загружает из архива, пока прежняя версия продолжает работать
- Останавливает стек (`docker compose down --remove-orphans`)
- Создаёт бэкап (если выбран)
- Обновляет `docker-compose.yaml`, `init.sql`, документацию в `docs/` и файлы HTTPS-входа в `proxy/`;
  сертификат в `certs/` остаётся как есть
- **Добавляет** новые переменные в конец `.env`, под комментарием `# Added in <version>` (существующие
  значения не меняются; пустой `AUTH_SECRET` или `CORE_SECRET` получает сгенерированное значение)
- Переводит `PUBLIC_URL` с `http://` на `https://` и добавляет `CERT_HOST` с хостом из него, если установка
  сделана до появления HTTPS-входа; оба изменения обновление печатает. Обновление останавливается до того,
  как что-либо остановлено или заменено, если в `.env` нет строки `PUBLIC_URL` или если нужно добавить
  `CERT_HOST`, а хост в `PUBLIC_URL` не читается или содержит что-то кроме букв, цифр, `.`, `-` и `:`.
  Обновление предупреждает, если этот хост - `0.0.0.0`, который браузер не откроет, и если `PUBLIC_URL`
  уже был `https://`: такая установка стоит за вашим собственным обратным прокси, и теперь он должен
  пересылать запросы на `https://` (см. [Свой обратный прокси](#свой-обратный-прокси))
- Запускает стек (если указан `--up`)

## Бэкап и откат

### Режимы бэкапа

| Режим   | Что сохраняется                             | Размер            |
| ------- | ------------------------------------------- | ----------------- |
| `files` | `docker-compose.yaml`, `.env`, `.xagent/state.json`, сертификат из `certs/`, файлы HTTPS-входа из `proxy/` | ~10 КБ |
| `full`  | Файлы + данные PostgreSQL (Docker volume)   | Зависит от данных |

Бэкапы сохраняются в `<install-path>/backups/<timestamp>/`.

### Откат

Если после обновления что-то пошло не так:

```bash
sudo ./xagent-installer rollback --path /opt/xagent
```

Откатит к последнему бэкапу: восстановит конфигурацию, данные (при `full` бэкапе) и запустит стек.

Для отката к конкретному бэкапу:

```bash
sudo ./xagent-installer rollback --path /opt/xagent \
  --backup-dir /opt/xagent/backups/2026-02-21T12-00-00-000Z
```

## Структура установки

```
/opt/xagent/
├── docker-compose.yaml     # Compose-конфигурация
├── .env                    # Переменные окружения (chmod 0600)
├── .env.example            # Пример базового набора переменных
├── init.sql                # Скрипт инициализации БД
├── proxy/                  # HTTPS-вход: конфигурация nginx, скрипт сертификата
├── certs/                  # tls.crt + tls.key, которые отдаёт HTTPS-вход
├── docs/                   # Пользовательская документация
│   ├── ru/                 # Русские тексты
│   └── en/                 # Английские
├── .xagent/
│   └── state.json          # Метаданные установки (версия, порт, даты)
├── logs/
│   └── installer.log       # Лог инсталлятора (секреты редактируются)
└── backups/
    └── <timestamp>/        # Бэкапы при обновлениях
```

## Управление стеком

Все команды выполняются из директории установки. Docker Compose автоматически подхватывает `docker-compose.yaml` и `.env` из текущей директории.

```bash
cd /opt/xagent

docker compose up -d       # Запуск
docker compose down        # Остановка
docker compose logs -f     # Просмотр логов
docker compose restart     # Перезапуск
docker compose ps          # Статус контейнеров
```

## HTTPS и сертификат

XAgent открывается по HTTPS через вход - службу `proxy` (nginx) на порту, выбранном при установке. Само
приложение наружу не опубликовано. Вход работает по HTTP/2: все соединения браузера с XAgent идут по
одному. Каждое открытое окно чата держит живое соединение, а по обычному HTTP/1.1 браузер разрешает
только шесть соединений к одному адресу - с седьмого окна страницы перестают загружаться.

Сертификат - два файла в `certs/`: `tls.crt` и `tls.key` (PEM). При первом запуске служба `cert-init`
делает самоподписанную пару для `CERT_HOST` (она подходит и для `localhost`, и для `127.0.0.1`), если в
папке пары нет; уже лежащая пара не трогается. О самоподписанном сертификате браузер один раз
предупредит.

Чтобы поставить сертификат организации или обновить его, положите новые файлы в `certs/` под теми же
именами и попросите вход перечитать их без перезапуска:

```bash
cd /opt/xagent
docker compose exec proxy nginx -s reload
```

### Свой обратный прокси

Если XAgent стоит за вашим собственным обратным прокси, этот прокси должен:

- пересылать запросы на `https://<host>:<port>`: опубликованный порт говорит только по HTTPS, а на обычный
  запрос отвечает переходом на `https://`;

- говорить с браузерами по HTTP/2 - без него одновременно работают не больше шести окон чата;
- передавать живые потоки по мере поступления, без буферизации: `/api/chats/<id>/events`,
  `/api/chats/<id>/stream` и `/api/targets/status/stream` (приложение и само шлёт `X-Accel-Buffering: no`);
- ждать между двумя чтениями от XAgent не меньше 10 секунд на этих потоках (они пишут каждые 8 секунд) и
  не меньше 300 секунд на обычных запросах;
- передавать `Host` с портом, `X-Forwarded-Host` и `X-Forwarded-Proto: https`: вход в систему строит по ним
  свои адреса и выбирает имена cookie.

## Переменные окружения

Переменные в `.env`. Визард записывает обязательные значения сам; остальные добавляются вручную по этому справочнику. Файл `.env.example` рядом с установкой показывает базовый набор строк - за полным перечнем настроек смотрите таблицы ниже. Значения в нём образцовые: секреты (`AUTH_SECRET`, `CORE_SECRET`, пароль базы) берите только те, что сгенерировал визард, иначе установка поедет с общеизвестными ключами.

Ядро (`xagent-core`) читает весь `.env`. Веб-интерфейс (`xagent-web`) получает только нужные ему ключи:
`PUBLIC_URL`, `AUTH_SECRET`, `AUTH_TRUST_HOST`, `CORE_SECRET`, `CORE_PORT` (в виде адреса ядра `CORE_URL`), `SQL_MODE`, `AUTH_OPENID_ID`,
`AUTH_OPENID_SECRET`, `AUTH_OPENID_ISSUER` и `TZ`; пароль базы и ключи моделей к нему не попадают.

### Обязательные

| Переменная          | Описание                 | Значение по умолчанию |
| ------------------- | ------------------------ | --------------------- |
| `PUBLIC_URL`        | Публичный URL приложения, `https://` | `https://<имя хоста>:8080` |
| `CERT_HOST`         | Хост, для которого делается самоподписанный сертификат | Хост из `PUBLIC_URL` |
| `POSTGRES_USER`     | Пользователь PostgreSQL  | `dbagent`             |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL        | Автогенерация         |
| `POSTGRES_DB`       | Имя базы данных          | `dbagent`             |
| `AUTH_SECRET`       | Секрет для JWT           | Автогенерация         |
| `CORE_SECRET`       | Секрет для core binary   | Автогенерация         |

Сохраняйте `CORE_SECRET` при перезапусках и восстановлении базы. Он также защищает хеши запросов, сохранённые для повторов через API. После его смены повторы для записей, защищённых прежним секретом, возвращают `422` до истечения срока записей — 24 часов. Ещё не защищённые старые записи сохраняют возможность повтора. Пока Core работает, планировщик удаляет просроченные записи и защищает до 100 старых хешей запросов в минуту. Старые резервные копии базы могут содержать прежние незащищённые хеши; смена секрета их не удаляет. Если такая копия стала доступна посторонним, смените пароли затронутых пользователей.

Писарь сохраняет полезные знания после затихшего разговора или закрытия записи о проблеме.

## Решение проблем

Ниже - отказы установщика и стека. Ошибки самого приложения, у которых уже есть обходной путь, собраны в [known-issues.md](known-issues.md).

### Docker не найден

```
✖ Docker Engine not found
```

Установите Docker по [инструкции](https://docs.docker.com/engine/install/).

### Порт занят

```
✖ Port 8080 is occupied
```

Освободите порт или выберите другой при установке. Порт публикует служба `proxy`. Проверить, чем занят порт:

```bash
ss -tlnp | grep 8080
```

### Образы не скачиваются

Установщик называет причину отдельно для каждого случая - общего «нет сети» не бывает.

- **Такой версии нет в хранилище** - код 13. Проверьте номер версии архива; архив собирается только
  после выкладки образа, так что расхождение означает битую или самодельную сборку.
- **Хранилище не отдаёт образ** - код 13. Docker Hub отвечает одинаково и когда образа нет, и когда он
  закрыт, поэтому сообщение называет оба варианта.
- **Исчерпан предел скачиваний** - код 13. Docker Hub ограничивает число скачиваний без учётной записи.
  Подождите сброса предела или возьмите архив с образами (`…-offline.zip`).
- **Данные перестали поступать** - код 13. Скачивание прервано после 10 минут без единого нового байта.
  Запустите заново: уже скачанное не качается повторно.
- **Не хватает места** - код 14. Место проверяется только под недостающие образы. Если каталог образов
  Docker недоступен с этой машины (демон живёт в своей виртуальной машине), установщик говорит, что
  измерить не может, и продолжает - отказать по неизмеримой величине он не имеет права.

### Другой запуск уже идёт

```
✖ Another xagent installer run is already in progress (process 1234, lock file /var/lock/xagent-installer.lock)
```

Код 15. Установка, обновление и откат берут общий замок - одновременно менять стенд им нельзя.
Дождитесь завершения первого запуска. Если тот процесс уже не существует, замок забирается сам.

Код 16 - другой случай: с самим файлом замка что-то не так, и сообщение говорит, что именно.
Замок остался от запуска под другим пользователем - удалите файл под тем пользователем, которому он
принадлежит, и запустите установщик заново.
Файл вообще не удалось создать - проверьте права на каталог `/var/lock` и запустите установщик заново.

### Установка оборвалась на полпути

Если каталог установки создан, но установка не завершилась, повторный `install` скажет об этом прямо и
подскажет, что делать: проверить содержимое каталога, удалить его и запустить установку заново.
Команда `update` в этом случае не поможет - обновлять ещё нечего.

### Ошибка целостности

```
✖ Bundle integrity check failed
```

ZIP повреждён при передаче. Скачайте заново и проверьте `SHA256SUMS`.

### Контейнеры не запускаются

XAgent работает в двух контейнерах: `xagent-core` (ядро: база данных, модели, расписания) и
`xagent-web` (веб-интерфейс). Веб-интерфейс запускается, когда ядро сообщит, что готово. Проверьте
логи обоих:

```bash
cd /opt/xagent
docker compose logs xagent-core xagent-web
```

Частые причины:

- Неверный API-ключ LLM → проверьте `.env`
- PostgreSQL не инициализирован → дождитесь healthcheck (~30 сек)

### Вход сообщает, что сервис недоступен

```
Sign-in is temporarily unavailable: your credentials could not be checked. This is not a problem with your password
```

Веб-сервер не получил ответа от ядра, поэтому пароль не проверялся. Причина - в логах веб-сервера
(`docker compose logs xagent-web`), в строке, которая начинается с `[auth]`. Окончание
`the shell and Core do not share the same CORE_SECRET` значит, что у двух контейнеров разные значения
`CORE_SECRET`: проверьте, что `.env` задаёт `CORE_SECRET` один раз и непустым значением, и примените его
командой `docker compose up -d`. Форма первого входа сообщает о той же причине текстом
`Setup could not be completed: the service refused the request before reading it`.

### Контейнер помечен `unhealthy`

`docker compose ps` показывает `xagent-core` или `xagent-web` в состоянии `unhealthy`. Это значит, что
ядро или веб-сервер перестал отвечать, хотя его процесс ещё жив.

Посмотрите ошибку того контейнера, который помечен:

```bash
cd /opt/xagent
docker inspect --format '{{range .State.Health.Log}}{{.End}} exit={{.ExitCode}} {{.Output}}{{end}}' xagent-xagent-core-1
docker inspect --format '{{range .State.Health.Log}}{{.End}} exit={{.ExitCode}} {{.Output}}{{end}}' xagent-xagent-web-1
```

Затем перезапустите этот сервис, например:

```bash
docker compose restart xagent-core
```

Контейнер, процесс которого не просто молчит, а завершился, поднимается заново сам по правилу
перезапуска - вмешательство не требуется. Счётчик перезапусков:

```bash
docker inspect --format '{{.RestartCount}}' xagent-xagent-core-1
```
